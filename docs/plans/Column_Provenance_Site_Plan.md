# Plan: a column provenance site on GitHub Pages

Drafted 31 October 2026, after postcode-simd's site (`docs/plans/Column_Provenance_Site_Plan.md`
there, live at https://mtinti.github.io/postcode-simd/). Status: proposed.

## Aim

A public site, regenerated on every push and published at `https://mtinti.github.io/uprn-epc/`,
with **one page per column** of `epc_domestic`. A reader given
`https://mtinti.github.io/uprn-epc/columns/current_energy_efficiency_int/` sees what the column
is, the published field it comes from, what was done to it, which checks guard it, and the
decision behind it. The site carries metadata only: no value of any row, no address, no
postcode, no count that singles out a dwelling. The repository is public, so the site publishes
nothing that is not already in it.

## What exists, and what does not

| Fact | Where it lives today |
| --- | --- |
| name, type, width, nullability, group, short description | `epc_ingest/output_schema.yaml` (130 fields: 3 key, 107 published, 20 derived), generated by `epc_ingest/columns.py` |
| the published field each column copies, its publisher label and width | `epc_ingest/published_columns.yaml` |
| the pinned sources: archive, note, 19 annual files, two data zone lists, hashes, licence, attribution, Zenodo draft | `epc_ingest/sources.yaml`, `data/sources/*/SOURCES.md` |
| the transformation of each derived column | `epc_ingest/reader.py`, one function per rule, and the `source` field of the schema |
| the checks | every check a build emits, with name, result and detail, in `results/manifest.json["checks"]` (295 in the 2026Q2 build); `BUILD_REPORT.md` summarises them |
| the reasons | `epc_ingest/decisions.yaml`, 12 entries |
| what is exported and as what in SQL Server | `epc_ingest/export_contract.yaml`, `epc_ingest/sql_check.py` |

Missing:

- **Descriptions.** 107 of the 130 fields say only "As published. Publisher's label: X". The
  pinned publication note (`publication_note.pdf`, SHA256 `c2f33696…`, 17 pages) defines every
  published field in its data dictionary, for example `INSPECTION_DATE`: "Date on which
  assessment of the energy performance of the building was undertaken". That text is the source.
- **A tested lineage.** The facts above are not joined per column anywhere.
- **`decisions.yaml` does not parse as YAML.** Line 17 (`why:` of `file-year-is-created-at`)
  holds an unquoted `: `. The build only hashes the file, so nothing has read it until now. The
  fix changes `decisions_sha256`, which is embedded in the Parquet and the manifest, so it goes
  in with the next rebuild, not on its own.
- **No `docs` extra, no MkDocs config, no Pages workflow.** All three exist in postcode-simd and
  carry over with the names changed.

## Design

### 1. Pages

- **One page per column**, 130. Sections: *What it is* (the note's definition for a published
  field, attributed; ours for a key or derived column, marked as ours); *Where it comes from*
  (the 19 annual files, the archive they were extracted from, hashes, licence); *The exact
  source field* (publisher label and machine name, position in the header); *What was done to
  it* (copied as text; or the rule, in words, with the function in `reader.py`); *How it is
  checked* (definitions, never results); *Why* (decision links); *In SQL Server* (declared type,
  nullability, whether it is indexed, whether a join compares it).
- **Index pages**: columns grouped as the data dictionary groups them (key, published in
  published order, derived); one page per pinned source object (the archive, the note, each
  annual file, each data zone list) listing what it feeds; one page per decision listing the
  columns it governs; one checks page defining every check family.
- **A home page** saying what the table is, what the site is not (no data), where the data
  dictionary, the loader and the joins are, and which Zenodo record holds the source.

### 2. The lineage map

`epc_ingest/lineage.py` returns one record per column, derived from the schema, the registry,
`published_columns.yaml` and the reader's constants, never typed by hand. A record holds:

- **inputs**: for a published column, the field of the same publisher label in each of the 19
  annual files (condition: the file's year), reaching the row by file position; for a derived
  column, the published column it reads (`source` in the schema) and, for the two data zone
  columns, the pinned zone list it is checked against; for the key columns, the registry's
  release and the file name and row position;
- **transformation**: `copied` for published text; for derived columns the rule in words and
  the function (`trimmed and cast to bigint`, `upper-cased, spaces removed, NULL when empty`,
  `S01 plus six digits, otherwise NULL, status says why`, `parsed yyyy-mm-dd`, `parsed
  dd/mm/yyyy hh:mm:ss`, `True/False to 1/0`, `integer or decimal(19,4) from the text`);
- **checks**: the definitions that guard it, by family: `source.*` (the pinned hash),
  `<year>.header_names` and `header_labels`, `row_width`, `utf8`, `text_within_width`,
  `rrn_shape`, `rrn_unique_in_file`, `created_at_year`, `derived_values_parse`,
  `decimal_round_trip`, `table.*`, `datazones_*`, `readback.*`, `schema.matches_generator`;
- **decisions**: ids from `decisions.yaml`;
- **export**: in the CSV (every column since `address-lines-loaded`), the SQL type, the index
  it carries, whether the digest covers it (every column does).

Simpler than postcode-simd's: one table, one source dataset, no computed-over-a-universe
columns. The site's value is the per-field definitions beside the checks and the reasons.

### 3. Descriptions: a reviewed source

`epc_ingest/column_descriptions.yaml`, one entry per column, each with text and source:

- **Published fields**: extracted once from the pinned note by a script (`tools/extract_note_dictionary.py`, pypdf,
  run with the script directory off the path since the PDF is a download), then reviewed
  against the PDF by eye, with the note's own label (for example "Date of Assessment") kept
  beside the machine name. Each entry records the note's hash and the page.
- **Key and derived columns**: written by us, marked as ours, with the decision behind them.
- A column without a description fails a test, so the gap is closed before the site publishes.

The schema's short descriptions stay as they are for the data dictionary.

### 4. Generation and publishing

- `python -m epc_ingest.provenance_site` writes Markdown to `build/provenance_docs/`;
  `mkdocs build` (Material theme, `strict: true`) renders `build/provenance_site/`. Both
  directories are gitignored.
- `.github/workflows/pages.yml` and `.github/scripts/pages_publish.sh`, copied from
  postcode-simd: tests first, then build, then push to `gh-pages`; `main` at the root, any other
  branch under `preview/<name>-<hash>/`, a deleted branch's preview removed; a pull request is
  built and tested only. The script requests a Pages build and fails unless one completes.
- GitHub Pages switched on for `mtinti/uprn-epc` from the `gh-pages` branch, by hand, once.
- `pyproject.toml` gains `docs = ["mkdocs==1.6.1", "mkdocs-material==9.7.7", "pypdf==6.14.2"]`.

### 5. Tests, `tests/test_provenance.py`

Mirroring postcode-simd's: every column has a lineage record and a description; every input
reference names a pinned object that exists in the registry; every decision id exists; every
cited check has a definition and is one the build emits (checked against the manifest's names);
the site has a page per column and every internal link resolves; a page never claims a check
passed; regeneration removes pages no longer written; no page contains a postcode-shaped string
or any of the fixture's address text; the note text is labelled as the note's wherever it
appears; `decisions.yaml` parses.

## What the site must never show

No row value, address, postcode, UPRN or RRN; no count from the manifest's observations that
could describe one dwelling. Counts the data dictionary already publishes (rows per year, empty
UPRNs) are fine. The generator reads the schema, registry, decisions, contract and descriptions
only; it never opens the Parquet, the CSV or a source file. A test asserts the generator's
imports.

## Phases

1. Fix `decisions.yaml` quoting with the next rebuild; add the parse test. (With the rebuild.)
2. Extract and review the note's dictionary into `column_descriptions.yaml`. (Half a day; the
   review by eye is the long part, 107 entries.)
3. `lineage.py` and its tests. (Half a day.)
4. `provenance_site.py`, `mkdocs.yml`, the site tests, a local build. (One day.)
5. Workflow, script, Pages switched on, first publish, link from the README. (Two hours.)

## Open questions

- Whether to show the manifest's check results for the current build on a per-build page, as
  postcode-simd's phase 2 proposed, or keep the site to definitions and point at the manifest.
  Proposed: definitions only, as postcode-simd does today.
- Whether the note's definitions may be reproduced verbatim. The note is published under the
  Open Government Licence apart from the address fields' notice, so quoting with attribution is
  allowed; the site will attribute every quotation to the note and its release.
